# Development

UI Eval is a public-source TypeScript ESM project built as a single modular monolith. The package remains private and unpublished. Bun manages the workspace; the built runtime targets Node.js 20 or newer.

This guide describes how to change the repository. It does not imply that any command has passed on a particular revision; run the required checks against the source you intend to review.

## Prerequisites

- Node.js satisfying `package.json#engines`.
- Bun matching `package.json#packageManager`.
- Git.
- Playwright Chromium for real-browser conformance tests.

Install dependencies without rewriting the lockfile:

```bash
bun install --frozen-lockfile
```

Install the browser only when capture development or conformance tests require it:

```bash
bunx playwright install chromium
```

On Linux CI, Playwright may require its documented system dependencies in addition to the browser binary.

## Source layout

```text
src/
  contracts/             schemas, types, canonical JSON, validators
  project/               authoring loaders and containment
  manifest-compiler/     scenario/policy materialization
  capture-playwright/    browser adapter and evidence collection
  evaluators/            implemented evaluator registry
  policy-engine/         deterministic gate AST
  runtime/               shared owned-process and bounded command primitives
  orchestrator/          pipeline, identity, server, cross-binding
  storage-local/         CAS and run store
  report-html/           static report view
  cli/                   commands, output, exits, signals
  agent/                 suite loader, pure assessment, bounded loop and reports
  integration/           engine pin, preparation, full acceptance and JSON/HTML
  index.ts               supported programmatic exports
schemas/                 generated JSON Schema artifacts
docs/                    Markdown source documentation
```

Keep internal dependencies directed toward contracts and narrow interfaces. Do not import candidate-application code, candidate aliases, fixtures, routes, environment variables, or framework-specific modules into the engine.

## Common commands

| Command | Purpose |
| --- | --- |
| `bun run ui-eval --help` | Run the source CLI through Bun. |
| `bun run design:check --css <path> --config <path>` | Fail closed when Tailwind-produced token facts drift from a sealed geometry config; does not rewrite either input. |
| `bun run test` | Run unit/contract tests; excludes `*.capture.ts`. |
| `bun run test:capture` | Run the opt-in real-browser conformance suite. |
| `bun run schema:generate` | Regenerate checked-in JSON schemas from TypeBox sources. |
| `bun run schema:check` | Verify generated-schema expectations. |
| `bun run lint` | Run ESLint. |
| `bun run typecheck` | Run TypeScript without emitting files. |
| `bun run build` | Build ESM library and CLI artifacts with tsup. |
| `bun run check` | Check schemas and generated docs, run unit tests, lint and typecheck, build, and verify the direct and symlinked dist CLI. |
| `bun run verify:integration` | Additional real-Chromium built-CLI check of a temporary prepared Web candidate; requires a clean engine checkout and current build. |

`bun run check` does not replace the real-browser suite. Changes to capture, browser routing, stabilization, auth state, evidence collection, or lifecycle require `bun run test:capture` as an additional gate.

## Change workflow

1. Inspect the affected module, its tests, public contract, and related docs.
2. State the intended behavior and truthfulness boundary before editing.
3. Add or update a failing focused test.
4. Make the smallest coherent implementation change.
5. Run focused tests while iterating.
6. Run the verification ladder appropriate to the risk.
7. Scan every surface that repeats the changed fact: schema, types, validators, CLI help, examples, docs, changelog, report renderer, and policy defaults.

Generated files must be regenerated by their owning script, not edited by hand.

## Contract changes

Public contract work has a higher bar because a structural pass can still be semantically unsafe.

For every contract change:

- update the TypeBox authoring source;
- derive types rather than creating duplicate interfaces;
- regenerate `schemas/*.schema.json`;
- update structural and semantic validators;
- add valid, malformed, digest-mismatch, and round-trip tests;
- test every compiler/adapter/evaluator/report consumer;
- decide whether the change is additive or breaking for `uieval.io/v1alpha1`;
- document migration and changelog impact;
- keep examples schema-valid in CI once executable examples exist.

Canonical digest exclusions must use a named contract profile. Do not add a broad global exclusion to make a failing digest test pass.

## Capture and security changes

Browser behavior is security-sensitive. A change to routing, redirects, popups, auth storage state, service workers, egress, assertion serialization, evidence budgets, or context shutdown requires:

- pure classification/contract tests where possible;
- a real Chromium case for browser-observable behavior;
- a negative case proving the external destination or unsafe data is not requested/persisted;
- capture-status monotonicity checks;
- updates to [Security model](security-model.md) and [Current limitations](limitations.md).

Do not weaken a boundary merely to make a third-party-dependent scenario pass. Add a same-origin proxy or deterministic fixture, or keep the result inconclusive.

## Storage changes

Local storage is project/store scoped. Test:

- atomic writes and concurrent puts;
- lexical and real-path containment;
- symlink, non-regular file, and corruption cases;
- size and digest verification;
- scope mismatch;
- monotonic per-digest sensitivity;
- conservative behavior for metadata-less objects;
- namespace isolation across storage-format versions.

Changing a storage invariant requires a new store ID or an explicit migration tool. Never make the normal read path guess how to upgrade old bytes.

## Report and CLI changes

Machine interfaces must remain deterministic:

- JSON mode writes one JSON value to stdout and progress to stderr;
- candidate raw stderr stays withheld;
- exit codes preserve product/infra/review distinctions;
- HTML escapes untrusted strings and uses local relative links;
- report provenance lists only evaluators actually executed;
- pre-plan failures do not pretend a sealed run exists;
- post-plan failures attempt a truthful report when storage permits;
- cancellation retains `130`/`143` semantics and cleans only owned processes.

Use golden tests for CLI output and cross-contract tests for report changes. Never use HTML as an alternate source of result semantics.

## Fixtures and test data

All fixtures must be synthetic and minimal. Do not add:

- real cookies, tokens, API keys, or storage state;
- customer or employee data;
- production URLs or internal repository credentials;
- unredacted browser traces from a real account;
- candidate-specific business content in generic engine tests.

Security fixtures should demonstrate the smallest hostile condition needed for the test.

## Documentation rules

- Markdown is the canonical documentation source.
- Do not hand-copy full schema definitions into prose.
- Label current, forward-contract, and planned behavior explicitly.
- Do not claim tests passed without running them on the stated revision.
- Do not claim package publication, support, or licensing beyond the configured public source repository and `UNLICENSED` status.
- Update `CHANGELOG.md` under `Unreleased` for user-visible behavior.
- If a generated HTML reading view is retained, regenerate it from its Markdown source and verify its source digest; never edit it independently.

## Verification ladder

Choose the smallest sufficient start, then finish with the gates for the affected surface.

### Documentation-only

```bash
bun run lint
bun run typecheck
```

Also check local Markdown links, capability wording, and forbidden project-specific content. If documentation sync tests exist, run them explicitly.

### Contracts, compiler, evaluator, policy, storage, report, or CLI

```bash
bun run schema:check
bun run test
bun run lint
bun run typecheck
bun run build
```

`bun run check` is the shorthand for this non-browser set.

### Browser/capture/lifecycle

Run the non-browser set and:

```bash
bun run test:capture
```

When a change affects actual candidate orchestration, also run `doctor` and an end-to-end scenario against a synthetic project fixture. Record exact commands and outcomes in the review, not in timeless architecture prose.

### Packaging readiness

Before any package-distribution decision, inspect the built tarball shape from a clean state and install that artifact into a clean synthetic consumer. The public source repository is not a package publication channel, so this remains a readiness check rather than a publish instruction.

## Review checklist

- [ ] Current behavior, schema, tests, docs, and changelog agree.
- [ ] Required evidence cannot become pass when missing or corrupt.
- [ ] Product, infrastructure, and advisory failures remain distinct.
- [ ] No candidate-specific source, fixture, path, route, port, or secret entered the engine.
- [ ] No new arbitrary code execution path was introduced.
- [ ] Sensitive evidence cannot acquire a weaker alias or metadata label.
- [ ] Browser and process cleanup remain bounded and ownership-safe.
- [ ] Forward-looking types are not documented as implemented runtime support.
- [ ] Verification commands were run and their actual outcomes reported.
